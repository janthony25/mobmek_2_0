### `car-make-model.md` — merged into `CarMakes`/`CarModels` (2026-10-12)
Previously zero code references anywhere; the only real seeding was `Data/CarReferenceDataSeeder.cs` (~10 hardcoded makes, skipped once the table had any rows — couldn't merge into an already-populated table). Rather than wiring the `.md` file into app code (it's a one-time reference bootstrap, not an ongoing input), merged it directly into the database with a generated, idempotent SQL script: for each of the file's 69 makes / 1231 models, `INSERT ... WHERE NOT EXISTS (... LOWER(...) = LOWER(...))` — same case-insensitive find-or-create semantics as `MakeModelResolver` (the legacy importer's resolver), just expressed as SQL instead of reusing that C# class directly. Run on local first (31→73 makes, 211→1319 models) and verified zero case-insensitive duplicates in either `CarMakes` or `CarModels` before running the identical script on EC2 (same before/after numbers, pre-merge `pg_dump` taken first). Purely additive — no rows deleted or updated, so no existing `Car` row's make/model reference could be affected.

The generated SQL script itself wasn't committed (one-off, not reusable tooling) — if `car-make-model.md` gets extended later, the same approach (regenerate a dedup-checked SQL script from its JSON, run on local then EC2) applies again.

### Duplicate detection — Working (fixed 2026-10-07)
Two different policies by design, per owner decision: customer phone/email is a **soft warning** (people legitimately share phones/emails — e.g. a family); car rego/VIN is a **hard block** (one physical car, one record — a collision is always a data-entry mistake).

- **Customer (soft):** `GET /api/customers/check-duplicate?phone=&email=&excludeId=` (`CustomerService.CheckDuplicatesAsync`) matches on phone (whitespace/dash-insensitive) and/or email (case-insensitive), returns up to 5 lightweight matches, never blocks. `CustomerForm.tsx` (new — replaces the generic schema form previously used by both `CustomersPage.tsx` and `CustomerDetailPage.tsx`'s edit modal, now consolidated into one component) calls this debounced (400ms) as phone/email are typed, shows a dismissible amber banner listing matches, and still lets the user save. Live-verified in-browser against real seeded data (correctly found two existing customers sharing a phone number).
- **Car (hard):** `CarService.ValidateUniqueAsync`, called from both `CreateAsync`/`UpdateAsync`, checks rego (always, case/whitespace-insensitive) and VIN (only when provided — blank VINs don't collide) against all other cars, returns `CarWriteError.DuplicateRego`/`DuplicateVin` → 400. **Important nuance:** the check only fires when the rego/VIN value is actually *changing* — production already has 7 pairs of cars sharing a rego from the legacy import (confirmed by querying the live DB), and without this exclusion, editing an unrelated field (color, year) on any of those 14 existing cars would have been wrongly blocked as colliding with its own pre-existing twin. A regression test (`UpdateAsync_AllowsEditingOtherFields_OnAPreExistingDuplicateRegoPair`) pins this down. Live-verified in-browser (adding a car with rego `FYN218`, one of the known-duplicate regos, was correctly rejected with "A car with this rego already exists.").

7 new backend tests on `CarServiceTests`/`CustomerServiceTests`.

### Customer creation requires a car — Working, atomic (added 2026-10-11)
The main "Add Customer" flow can no longer create a customer with zero vehicles — the strongest available guard against duplicate customers, since rego uniqueness is already a hard block: if a customer can't exist without a car, and that car's rego is already taken, staff are forced to find the real existing customer instead of creating a new one. (This doesn't fully replace the phone/email soft check above — it doesn't catch "same person, genuinely different car each visit.")

- **Backend:** new `POST /api/customers/with-car` (`CreateCustomerWithCarRequest` → `CustomerService.CreateWithCarAsync`) creates the `Customer` and `Car` in one unit of work — nothing is saved to either table until a single final `SaveChangesAsync`. `CarService.BuildAsync`'s customer-existence check was extended to also accept a `Customer` that's `Added` but not yet saved in the current change tracker (previously only checked the database), which is what lets this reuse the exact same make/model + rego/VIN validation `CarsController`'s own create path uses, with zero duplicated logic. On any car-side validation failure (bad make/model, duplicate rego/VIN), the tracked customer is detached and nothing is persisted — not even the customer — so a rejected attempt never leaves an orphan customer-with-no-car behind. 3 new tests, including the atomicity regression (`CreateWithCarAsync_DuplicateRego_PersistsNeitherCustomerNorCar`); 650/650 backend tests passing.
- **Frontend:** `CustomerForm.tsx` now also collects a full car (make → model cascading select, year, rego, VIN/color/engine optional) whenever `initial === null` (creating), reusing the exact same cascading-select pattern as `CarForm.tsx`. Editing an existing customer is unchanged — no car fields shown, since cars are managed from the customer's own detail page. `CustomersPage.tsx`'s `onCreate` now calls `createCustomerWithCar` instead of the old plain `createCustomer`.
- **Verification:** `dotnet build`/`dotnet test` (650/650) and `tsc`/`build`/`lint` all clean. Not live-browser-verified this session — local Postgres now mirrors a real EC2 snapshot (via `scripts/sync-ec2-to-local.sh`) whose admin login isn't a known dev password, and fabricating a login via raw SQL into the Identity tables was correctly blocked rather than worked around. ### Standalone kiosk "Add Customer + Car" page — Working (added 2026-10-14)
A new fixed permission, `Permissions.AddCustomerAndCar` (`Services/Permissions.cs`), gates a dedicated self-service page at `/add-customer-car` (`pages/AddCustomerCarPage.tsx`) meant for a tablet handed to the customer — it reuses `CustomerForm` as-is (same combined customer+first-car fields, same `createCustomerWithCar` call) but with no sidebar/nav chrome at all, just a success screen with an "Add another" button that remounts a blank form for the next customer, and a small "Sign out" link (since there's no sidebar to sign out from otherwise).

- **Not an `[Authorize]` policy on the backend.** `POST /api/customers/with-car` deliberately stays open to any authenticated user — gating it would have broken staff's existing "+Add Customer" wizard on `CustomersPage.tsx` unless every staff account were also granted this new permission, which wasn't the goal (owner decision, 2026-10-14). The permission is enforced entirely client-side as a routing concern.
- **Kiosk takeover, frontend-only:** `App.tsx` wraps the whole normal `AppLayout` route tree in a new `KioskRedirect` (`components/auth/KioskRedirect.tsx`) that checks `user.permissions` — if a signed-in account's *entire* permission set is exactly `{ AddCustomerAndCar }` (nothing else), every path other than `/add-customer-car` redirects there, so that account can never see the sidebar or any other page regardless of what URL it hits. `/add-customer-car` itself is still gated by the ordinary `RequirePermission` pattern (same component used everywhere else), so a user without the permission gets redirected to `/customers` same as any other unauthorized route. Admins set this up by creating a role with only this one permission checked (`RolesPage.tsx`, `PERMISSION_INFO.AddCustomerAndCar`) and provisioning a dedicated account against it.
- **Bug found by the user, live (2026-10-14): signing out of the kiosk page and logging in as a different account (e.g. Admin) landed back on the kiosk page instead of the normal app.** Root cause: `RequireAuth.tsx`'s session guard remembers the current URL as `from` whenever the user becomes unauthenticated (`<Navigate to="/login" replace state={{ from: location.pathname }} />`) so a fresh login can return to where you left off — a reasonable default everywhere else, since previously no page was permission-restrictive enough for this to matter. Signing out *from* `/add-customer-car` means `from` becomes `/add-customer-car`; the **next** login on that browser/tablet inherits it regardless of who that is — and an Admin passes `/add-customer-car`'s own `RequirePermission` check trivially (Admin holds every permission), so they'd land straight back on the nav-free kiosk page with no obvious way out except manually typing a different URL (matches the reported "had to log in multiple times" — it only cleared once they happened to navigate elsewhere before signing out again). **Fixed** by special-casing `/add-customer-car` in `RequireAuth.tsx` to never be remembered as a `from` target. Also removed a redundant, unnecessary `navigate('/login')` call from `AddCustomerCarPage`'s own sign-out button that duplicated `RequireAuth`'s job — now matches the one established pattern used everywhere else (`Sidebar.tsx`'s sign-out just calls `logout()` and lets `RequireAuth` react).
- **Verification:** `dotnet build`/`dotnet test` (682/682) and `tsc -b`/lint all clean. **Not live-browser-verified by Claude** — same pre-existing gap noted below (local Postgres mirrors a real EC2 snapshot whose Admin password isn't a known dev credential, and the `.env` bootstrap admin never got created because an Admin already exists from the sync); confirmed via `curl` that the bootstrap dev credentials indeed 401, consistent with that note. The kiosk-redirect bug above was found by the user's own live testing, not caught by `tsc`/lint/the backend test suite (it's a client-side routing/UX issue with no test coverage) — relying on the fix's logic review plus the user's own re-test until a real login is available for a Claude-driven browser pass.

### Phone input now blocks letters at the keystroke level — Working (added 2026-10-12)
Found while investigating a legacy customer whose `PhoneNumber` field literally contained the text "GEORGE": `CreateCustomerRequest`/`UpdateCustomerRequest` already have `[Phone]` validation server-side (confirmed with a throwaway test — it rejects `"GEORGE"`/`"ABC123"`, accepts real numbers), so that bad value could never be saved through the app itself; it only exists because the legacy importer wrote straight to the database, bypassing DTO validation entirely. The actual gap was the frontend: `CustomerForm.tsx`'s phone `<input type="tel">` had no character filtering — `type="tel"` is only a mobile-keyboard hint, not a constraint — so a letter typed there wouldn't be rejected until the Save click hit the backend 400. Fixed with `onChange={(e) => setPhoneNumber(e.target.value.replace(/[^\d+\-\s]/g, ''))}`, stripping anything that isn't a digit/`+`/`-`/space on every keystroke, matching what the backend already accepts. `tsc`/`lint` clean.

Note: a separate shared `PhoneInput.tsx` component (country-code dropdown + its own sanitizer) already exists and is used by `AppointmentForm.tsx`/`ResourceForm.tsx`/`AppointmentDetailModal.tsx` — `CustomerForm.tsx` has its own bespoke raw input instead, which is where this fix landed. Consolidating onto the shared component would be a bigger UX change (adds a country selector) than was asked for here; flagged as a possible follow-up, not done.
