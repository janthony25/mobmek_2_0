## Details

### Invoice vs Quote — single entity, not separate tables
`Invoice.DocumentType` (`"Invoice"`/`"Quotation"`) + `Status` (`"Active"`/`"Rejected"`/`"Accepted"`). `InvoiceService.GenerateDocumentAsync` (lines 145-238) is the shared path for both, differing only in `DocumentType` and due-date policy (quotation = issue+30 days, hardcoded). `AcceptQuotationAsync` (lines 240-293) converts a quotation into a new Invoice row by copying its snapshotted lines; the original quotation is kept, flipped to `Accepted`. `MarkPaidAsync` explicitly rejects quotations (line 324) — structurally non-payable.

### Invoice numbering — Working, concurrency-safe (fixed 2026-10-07)
`SequenceNumber` = `MAX(SequenceNumber) WHERE DocumentType=X) + 1`, counted independently per doc type. **Fixed:** a unique index on `(DocumentType, SequenceNumber)` now backs this at the DB level (migration `AddInvoiceSequenceNumberUniqueIndex`, confirmed no pre-existing duplicates before adding it), and both generation call sites (`GenerateDocumentAsync`, `AcceptQuotationAsync`) go through a new shared `SaveWithUniqueSequenceNumberAsync` helper that retries (up to 5 attempts) with a freshly recomputed number whenever a concurrent generation wins the race first — detected via `Npgsql.PostgresException.SqlState == UniqueViolation`. Live-verified: generated a real quotation post-fix, got the correctly-continued `QUO-0183` — **but against the local dev stack, not production** (see outage note below).

Prefix is configurable (fixed 2026-10-07) — see `business-settings.md` ("Invoice numbering prefix"); the numeric sequence itself is still a fixed 4-digit zero-padded format.

**Production outage, same day:** this fix and the prefix migration (`AddInvoiceQuotePrefixToBusinessDetails`) were committed and deployed (code only — `scripts/deploy.sh` never touches the DB by design) but the corresponding migrations were never actually run against the production database, per `infrastructure-deployment.md`'s already-documented deploy-mechanism gap. Result: every "Generate Invoice"/"Generate Quotation" on the live site threw a generic 500 (reading `BusinessDetails.InvoicePrefix`/`QuotePrefix`, columns that didn't exist in prod yet), reported by the user from their phone. Fixed later the same day by generating the idempotent SQL (`scripts/generate-migration-script.sh`) and applying it to prod via `psql` after a `pg_dump` safety backup, per the documented procedure — confirmed via `__EFMigrationsHistory` that all 4 pending migrations (the two above plus `AddEmailTemplate`/`AddReminderAndAppointmentEmailLinks` from the same day's email-module commit) are now applied. Not independently re-verified by generating a real invoice on production after the fix — ask the user to confirm it works now.

### GST calc — Working
Pulls the live GST rate at generation time and **snapshots** it onto the invoice (`GstRate`/`TaxAmount`) — later global rate changes don't retroactively affect issued invoices (tested). GST treated as tax-inclusive, applied on discounted subtotal.

### Payment tracking + ledger — Working
`MarkPaidAsync` stamps paid fields and posts a real cash-flow ledger entry routed to configured cash accounts by cash/card split, with guards against archived/missing accounts. `RejectAsync` reverses ledger postings. Heavily tested (34+ tests covering routing, idempotency, rejection cleanup). **`CashAmount`/`CardAmount`/`AmountPaid`/the ledger posting are unchanged by partial payments below** — `MarkPaidAsync` still always settles the full `TotalAmount` in one lump on the mark-paid date, regardless of any partial payments already recorded (see gap in `feature-gaps.md`). The generated PDF no longer shows a "Paid" banner at all for now (see below), so this discrepancy isn't currently visible to customers either way.

### Partial payments — Working, record-keeping only (added 2026-10-13)
New `InvoicePartialPayment` entity (`Entities/InvoicePartialPayment.cs`) and four endpoints on `InvoicesController`: `POST .../partial-payments`, `PUT .../partial-payments/{paymentId}` (notes), `PUT .../partial-payments/{paymentId}/visibility` (show-on-invoice toggle), `DELETE .../partial-payments/{paymentId}` — backed by `InvoiceService.{Add,UpdatePartialPaymentNotes,SetPartialPaymentVisibility,DeletePartialPayment}Async` (`Services/InvoiceService.cs`). An invoice's `RemainingBalance` (on `InvoiceDto`/`InvoiceListItemDto`) is always computed as `TotalAmount - Sum(PartialPayments.Amount)`, never stored. Amount is validated `0 < amount <= remainingBalance`; blocked once the invoice is rejected, a quotation, or already fully paid. `Notes` text and `ShowOnInvoice` are the only fields editable after creation — amount/date/mode are locked.

**Never touches `Invoice.Notes` or the job's `JobNotes`/`InvoiceNotes`** (fixed same day, 2026-10-13) — an earlier version of this appended a timestamped line into those fields, which meant internal payment-tracking text showed up on the customer-facing generated invoice PDF (`Invoice.Notes` prints there) and cluttered the job edit form. Reverted: those three fields stay purely free-text, and history is surfaced only via `InvoiceDto.PartialPayments`/`InvoiceListItemDto`. The frontend instead shows a read-only list (`PartialPaymentHistoryList.tsx`) — used inside the Partial Payment wizard itself (`PartialPaymentForm.tsx`) and above the job form's Invoice Notes field (`JobForm.tsx`/`JobDetailPage.tsx`, aggregated across every invoice on the job) — with its own per-row "Show on invoice" checkbox, "Edit note", and "Delete" controls, never a shared text field. `InvoicesSection.tsx` gained an `onInvoicesChanged` callback (fired after reject/pay/partial-payment) so `JobDetailPage.tsx`'s own copy of this list refreshes immediately after an action in the wizard, not just on next page load.

**Opt-in "Show on invoice" per payment (added 2026-10-13):** `InvoicePartialPayment.ShowOnInvoice` defaults `false` — recording a payment never changes a customer-facing document on its own. Only payments explicitly toggled on (via the checkbox in `PartialPaymentHistoryList.tsx`, calling `SetPartialPaymentVisibilityAsync`) print on the generated PDF. When shown, they render as plain lines appended directly after the free-text Notes lines, inside the same "Notes" block — no separate "Payment History" heading (an earlier same-day version had one; dropped per feedback — "just a new line text after the actual notes"). Read live from `invoice.PartialPayments.Where(p => p.ShowOnInvoice)` at render time, not stored text. Covered by `InvoicePdfServiceTests.GenerateAsync_DoesNotThrow_When{InvoiceHasPartialPayments,PartialPaymentIsToggledVisible}`; not pypdf-verified against real extracted text this session (no live auth session available — see `feature-gaps.md`).

**"Paid" banner disabled (2026-10-13):** `InvoicePdfService` no longer renders the green "Paid {date} · Mode: X · Amount: Y" banner at all (`showPaidBanner` const, currently `false`) — per the user's explicit request, citing some invoices paid long ago but still unmarked `IsPaid` and a concern about payment-date accuracy if those get marked paid now (note: Mark Paid's "Date paid" field already supports backdating, `MarkPaidForm.tsx:91-92` — the exact remaining worry wasn't specified; see `feature-gaps.md`). The settle-amount-at-mark-paid fix from earlier the same day (not the full lifetime `AmountPaid`, to avoid double-counting partial payments) is left in place behind the flag for whenever this gets re-enabled.

**Deliberately does not post to the Cash Flow ledger** — see the open gap in `feature-gaps.md`. An earlier version of this change did post each partial payment as its own `CashTransaction` and made `MarkPaidAsync` settle only the remaining delta, but that doubled the surface area for a simple request; reverted to keep the first cut to record-keeping only.

Frontend: `PartialPaymentForm.tsx` (shared by all three invoice-action call sites — `InvoicesSection.tsx`, `DocumentListPage.tsx`, `CustomerDetailPage.tsx` — same pattern as `MarkPaidForm.tsx`) fetches the full invoice on open, shows existing payments with "Edit note"/"Delete" controls (delete gated behind `ConfirmDialog`), then the new-payment fields (mode/amount/date/notes) validated against the live remaining balance.

Backend tested: 11 new `InvoiceServiceTests` covering remaining-balance math, notes history append/edit/regenerate-on-delete, validation guards (amount bounds, already-paid, rejected/quotation), and the reject-blocked-while-partial-payments-exist guard. **Not live-browser-verified** — no browser extension available this session (see `feature-gaps.md`).

### Invoice PDF — Working, single renderer (fixed 2026-10-07)
Previously two separate, non-overlapping implementations existed: the real server-side QuestPDF renderer (`InvoicePdfService.cs`, only ever invoked from the email-attachment path) and a completely separate `InvoicePrintPage.tsx` that re-fetched JSON, rendered its own HTML, and called `window.print()` — what "View/Download PDF" actually showed. Users never saw the QuestPDF output; the two could drift.

**Fixed:** `InvoicePrintPage.tsx` is deleted, and its route removed from `App.tsx`. `InvoicesController` gained `GET /api/jobs/{jobId}/invoices/{id}/pdf` (`?download=true` toggles `Content-Disposition: attachment` vs inline), backed by the same `IInvoicePdfService.GenerateAsync` the email path already used — one renderer now, used everywhere. All four frontend call sites (`DocumentListPage.tsx`, `InvoicesSection.tsx`, `QuotationsSection.tsx`, `CustomerDetailPage.tsx`) repointed at the new endpoint via the pre-existing (previously unused) `apiUrl()` helper in `api/client.ts`; the redundant third "Print" menu item (a small popup that relied on the old page's auto-print JS, meaningless against a raw PDF) was dropped from `InvoicesSection.tsx`/`QuotationsSection.tsx` for consistency with the other two call sites' two-action (View/Download) pattern. Live-verified via curl: inline response has no `Content-Disposition` header and renders as a valid 1-page PDF; `?download=true` adds `Content-Disposition: attachment; filename=INV-0586.pdf` — both confirmed real PDF bytes.

**Bug fixed 2026-10-12 — Notes lost their line breaks:** `Invoice.Notes` (sourced from the job's `InvoiceNotes`, which the job page renders with `whitespace-pre-wrap` so a user's line breaks show on screen) was rendered in the PDF as a single `notes.Item().Text(invoice.Notes)` — QuestPDF's `Text()` treats the whole string as one wrapped paragraph and silently drops embedded `\n`, so multi-line notes came out as one run-on line in the generated invoice/quotation, same renderer for both (`InvoicePdfService.cs`). Fixed by splitting on `ReplaceLineEndings("\n").Split('\n')` and emitting one `notes.Item().Text(line)` per line (one `Column` item per line, matching the rest of this file's layout idiom). New regression test (`GenerateAsync_DoesNotThrow_WhenNotesSpanMultipleLines`, covering `\r\n`, a blank line, and a trailing newline) plus live verification: generated a real PDF with multi-line notes and extracted its text with `pypdf` — confirmed each line renders separately instead of concatenated.

**Layout changes (2026-10-11, `todo/miroboard-task.md`):** `ComposeHeader` now renders, in order: the phone/telephone/email contact line, `Website` on its own line (was previously joined inline with the contact line), then the bank-details "Payment details" block (moved from the bottom of the document, where it sat under the quotation-validity note). `ComposeContent`'s "Bill to" block now shows the customer's phone/email under their name, and an `Odometer: {n}` line under the car description when the job's `Odometer > 0`. Verified live against the real dev stack: generated a real invoice and a real quotation PDF (real customer/job/business data) and extracted the text with `pypdf` to confirm the actual rendered order, not just that generation didn't throw.

### Send Email — Working, fully traced end to end
`EmailComposeModal` → `sendInvoiceEmail` → `POST /api/jobs/{jobId}/invoices/{id}/email` → `InvoicesController.SendEmail` → `OutboundEmailService.SendInvoiceEmailAsync` → composes HTML + builds a real PDF attachment (via `InvoicePdfService`) → writes a `Queued` audit row → `ResendEmailSender` makes a real HTTP POST to `api.resend.com`, retries once on 429/5xx → row updated to `Sent`/`Failed`. A background `OutboundStatusPollJob` later upgrades status to `Delivered`/`Bounced`/`Complained` via a one-way rank so a late "Delivered" can't overwrite a "Bounced". Gated on `ResendConfigured`; shows a clear "not configured" message otherwise. See `email-module.md` for the shared pipeline detail. Used identically from both the global invoice/quote lists and the customer detail page.

**Multiple CC recipients (added 2026-10-12):** `EmailComposeModal.tsx`'s single CC field is now a list (`ccList: string[]`, starts with one empty row) with "+ Add CC" and a per-row "Remove" button; on submit the non-empty entries are joined into one comma-separated string for the existing `cc` field on `SendInvoiceEmailRequest` — no backend change needed, `OutboundEmailService` already accepted a comma-separated `cc`. `ReminderEmailModal.tsx`/`AppointmentEmailModal.tsx` (see `email-module.md`) were not touched — still single-CC.

### Catalog-service surcharge folds into the invoice line (added 2026-10-12)
A `JobServiceLine` can now carry an `AdditionalAmount` surcharge on top of its snapshotted catalog price (see `jobs-workshop-floor.md`). `InvoiceService.GenerateAsync`'s service-line mapping sets `ItemPrice = line.UnitPrice + line.AdditionalAmount` (with `ItemTotal = line.LineTotal` unchanged) so the generated invoice/quotation shows one consolidated price per line — e.g. a $200 catalog service with a $50 surcharge prints as a single $250 line, never a separate "+ $50" breakdown. Covered by `InvoiceServiceTests.GenerateAsync_FoldsServiceLineAdditionalAmount_IntoOneConsolidatedPrice`.

### Invoices/Quotations sections hidden during job edit (added 2026-10-12)
`JobDetailPage.tsx` no longer renders `InvoicesSection`/`QuotationsSection` at all while the job is in edit mode (`mode === 'edit'`) — not just the "+ Generate" buttons, but the whole list (view/download/email/accept/reject actions included). They're unnecessary clutter mid-edit and reappear as soon as the user hits Save or Cancel back to view mode. No backend change.

### Public Booking — backend real, frontend doesn't exist
`PublicBookingController.cs`: `[AllowAnonymous]`, origin-allowlisted CORS, explicit rate-limit policies. `PublicBookingService.cs` is a genuine NZ-timezone-aware (`Pacific/Auckland`) slot engine: 30-min slot grid, 60-min appointments, 8-week horizon, Sunday-closed, DST-safe, rejects double-booking/past-slots/out-of-horizon, enqueues a calendar-sync item on success. 19 tests covering edge cases.

**But `grep` across the entire frontend for `public/booking`/`PublicBooking` returns nothing — no route, no component, no API module anywhere, and no separate marketing-site repo exists.** The backend shipped 2026-08-07, after the industry-readiness doc (2026-08-04) flagged "no public booking page" as a gap — so the doc is now stale on the backend point, but still correct that there's **no customer-visible way to use this feature.**

**Decision (2026-10-07): deliberately deferred.** Building a public, unauthenticated booking page is a real scoping exercise (standalone route in this app vs. a separate site, branding, which fields to collect) — not a quick fix. Left as a documented gap for a dedicated session.
